Reason Network 是什么

Reason Network 是一个用 Rust 写的小守护进程，每台电脑跑一个。装上之后，你和队友电脑上的编程 Agent（Claude Code、Codex、Cursor、Gemini CLI 等）能互相看到对方：谁在线、在哪个仓库和分支、正在忙什么，并且可以直接给对方的某个会话发消息。消息端到端加密、点对点传输，Agent 通过名为 reason-network 的 MCP 服务拿到 list_team、send_message、check_inbox 这几个工具。

我平时在 Windows 上用，也用智谱的 ZCode Desktop，这两块恰好是它支持得最薄的地方，于是有了下面四个 PR。

#37 ZCode MCP 接入（已合并）

问题：ZCode Desktop 要手动配置 MCP 才能加入网络，其他 Agent 都是 setup 一条命令搞定。

做法：把 ZCode 加进已有的 setup、doctor、setup --remove 适配器注册表。按 ZCode 文档里的配置优先级来写：用户级的原生 mcp.servers 一旦存在，会整个盖住同级的 .agents/mcp.json，所以 setup 只改当前生效的那份配置，不动其他 MCP、模型和服务商设置，写之前先备份。

验证：cargo test 60 个测试通过，其中 11 个是 ZCode 配置的回归测试。然后在真的 ZCode Desktop 3.15.3 上跑：可执行文件放在带空格和中文的路径里，一段真实的 ZCode 对话调用了 list_team、send_message、check_inbox，收到 Codex 发来的 ping 并回了 ACK。测完把原配置逐字节还原。

顺带发现一个坑：check_inbox 等 60 秒会超过 ZCode 30 秒的工具执行上限，在这个宿主里要用更短的等待。

评审：维护者先要求修改，提了五点：

  1. 像其他适配器一样按名字 reason-network 认领配置项，而不是按可执行文件路径。否则二进制换了位置，setup 会拒绝、remove 会漏删。
  2. 去掉对当前工作目录的检查。否则在某个 .agents/mcp.json 坏掉的项目里跑 setup 会失败。
  3. 保持小巧：去掉自定义的管理标记和第二次备份（公共写入函数已经会备份）。
  4. README 写一两行就够，优先级的细节放进代码注释。
  5. 安装向导里的 Agent 列表漏了 ZCode。

最后维护者直接在我的分支上把这些改完合并了，说会随下一个版本发布。现在 README 里有了一条 “ZCode Desktop too”。

#160 ZCode 会话 Hooks（审核中）

问题：#37 之后 ZCode 已经能收发消息，但得自己调用 check_inbox 才看得到，别人发来的消息不会主动出现。

做法：利用 ZCode 的 Hooks。会话启动（SessionStart）时登记真实的会话；会话工作中每次工具调用后（PostToolUse），把待收的消息作为 additionalContext 注入进去。不加 Stop hook，也不做空闲唤醒。

可靠性上花的功夫最多：

  • Hook 只连已经在跑的守护进程，每次请求最多 1.5 秒，不会拖住 ZCode。
  • 消息先”租出”，hook 的输出本身不算签收；只有对应的回复或显式读收件箱才确认。没确认的消息在 90 秒租期过后或守护进程重启后会重发。也就是”至少一次”送达，不承诺恰好一次。
  • ZCode 里收件箱的等待上限改为 5 秒，避开那个 30 秒限制。

验证：cargo test 252 个通过；另写了一个端到端脚本，对着隔离的真实守护进程跑了 28 项检查，覆盖两个会话的路由、重复触发、中文和空格路径、守护进程卡死时的超时、重启恢复、文件夹退出网络、附件限制在工作区内等。早先的版本在真实 ZCode Desktop 上，两个对话共收到 5 条不同的消息并回了 ACK，全程没调用 check_inbox。

现状：维护者已排进审核队列。10 月 30 日维护者留言说，最近两天主干从 v0.12.14 更新到了 v0.12.17，跟这个 PR 起了冲突，需要 rebase 后再审。

#161 Windows 原生桌面目录（草稿）

问题：Windows 上有守护进程和命令行，但没有窗口可以看团队目录（macOS 有菜单栏图标）。

第一版用 Tao/Wry（WebView）做界面。维护者回复说：Reason Network 跑在每个人的电脑上还会自动更新，所以依赖要尽量小，每加一个都要仔细看；WebView 这一整套会往 Cargo.lock 里带进很多新 crate，先暂停，等他们决定。

改写：我把界面换成了 Win32 原生控件（列表视图、编辑框、按钮、系统剪贴板），只用项目里本来就有的 windows-sys。结果 Cargo.lock 和上游逐字节相同，比第一版少了 110 个依赖包。

窗口能看到团队和机器的连接状态、各会话地址、项目和分支、当前活动、未读数，支持中文搜索、”工作中/未读”筛选、复制地址和邀请链接、键盘导航和高 DPI。它是只读的：不启动守护进程、不注册 Agent、不消费消息、不改配置，关掉窗口守护进程照常运行。

验证：默认构建和 desktop 特性下各 251 个测试通过；在隔离环境里手动过了一遍真实窗口：中文路径搜索、空状态、断线显示和自动重连、复制的地址逐字比对等。多机真实场景和长时间运行还没测，PR 里也写明了。

#176 Windows 安装脚本的路径（待审核）

问题：install.ps1 会把安装目录和临时目录里的方括号当成 PowerShell 通配符。安装目录名像 bin [stable] 这样时，旧的可执行文件和备份会找不到；临时目录带方括号时，新的可执行文件挪不过去，解压出来的文件也会留在那里。

做法：查找、清理备份、移动可执行文件（包括回滚）、清理临时目录，全部改用 -LiteralPath。不碰依赖和引擎代码。

验证：给 Windows CI 加了一套 PowerShell 5.1 回归测试，跑真的安装脚本，下载部分用本地 ZIP 和校验和替身。七个用例：普通路径、全新安装、替换被占用的旧文件、注入失败后回滚、校验和不符、bin 和临时目录里带方括号/空格/中文。修复前六个失败，修复后七个全过。

几点收获

  • 跟着项目已有的写法走。 #37 被要求改的五点里有四点是”做多了”：按路径严格认领、工作区检查、自定义标记和额外备份、过长的 README。按名字认领配置、复用公共写入函数，就是其他适配器的做法。
  • 依赖是要花代价的。 对一个装在每个人电脑上、还会自动更新的程序，一套 WebView 依赖本身就是问题。换成原生控件以后，一个新依赖都没加。
  • 在真实环境里测。 30 秒工具超时、方括号被当通配符，这些都是在真实 ZCode、真实 Windows 路径上才暴露出来的。
  • 写清楚没测到什么。 每个 PR 都单独列了”哪些没有验证”，不把本地结果说成 CI 结果。
